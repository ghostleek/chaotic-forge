# PC-06 — Save the whole evolved game and play it again later

**Status:** Local issue draft; no GitHub issue/PR created, verified, or assigned.
**Proposed accountable owner / implementer:** Lance. **Reviewer:** Kahhow, independent of implementation.

## Outcome

After the group ends, its last actually played build and evolution history become a durable immutable artifact. A later visit can play that same game or start a new remix without changing the original or regenerating a different recipe.

Read [PRD](../../PRD.md), [PLAN](../../PLAN.md), [QUALITY](../../QUALITY.md), [AGENTS](../../AGENTS.md), PC-01/02/03 contracts, and the replay/data-availability findings in [prior review](../../archive/2026-09-13-mechanic-lab/mechanic-forge-pr-review.md). Replay here means fresh playable attempts; no historical video or player-path playback is promised.

## Scope and file ownership

Allowed: `lib/party-forge/archive.ts`, `lib/party-forge/runtime-registry.ts`, `lib/party-forge/server/archive-service.ts`, `app/api/party/rooms/[roomId]/archive/route.ts`, `app/api/party/archives/[archiveId]/route.ts`, `app/api/party/import/route.ts`, `db/schema.ts`, new `drizzle/**` migrations, `tests/party-archive.test.mjs`, and `tests/integration/party-archive.*`. Lance owns archive, persistence, and shared version registry. PC-07 owns display/download controls. Retaining runtime/assets may require an explicit handoff to their owner; never silently edit old versions.

Persist immutable manifest, exact resolver/catalog/runtime/assets versions, seed/scoring policy, contributions, and round history. Bind the archive to the group's last completed played revision; omit pending/failed edits. Append bounded history records instead of growing one unlimited room blob. Keep transient participant/host capabilities out of archives and exports.

Provide durable archive retrieval and a portable JSON export/import with schema, size, version, and reference validation. New play/remix creates a fresh room and participants; old identities, scores, edit permissions, or secrets never become new-room authority. Proposed saved-remix setup lets each new player keep or replace one inherited FPS/Zombies/Cooking slot using its two supported variants; inherited later additions remain. Record replacements as new fork decisions and keep the source archive immutable. If all choices are kept, label it Play again. Missing executable versions must produce a clear unavailable state rather than automatic regeneration or silent substitution.

Preset runtimes/assets can remain in an immutable static version registry. Prove the retention mechanism survives a later deployment. Compact metadata belongs in D1; R2 is not required unless actual dynamic artifacts are introduced later. A download alone is not the promised hosted save. State archive retention separately from the room inactivity TTL and provide a portable preservation route.

Prove save is idempotent, an unplayed failed build is excluded, remix does not mutate its source, and imports reject invalid/unsupported data without erasing current work. Remix an archive with all three additive cards already present: slot replacement must still produce a valid new match without erasing inherited additions; all-kept choices remain Play again. Verify two deployment versions can still play the older archive. Validate capability separation and storage-failure recovery.
