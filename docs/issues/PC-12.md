## Smallest playable rules

1. The player stays at a fixed horizontal position while the course scrolls left.
2. A fresh **Jump** press starts upward velocity only while grounded; gravity returns the player to the floor. Space and a visible Jump button map to the same logical input.
3. Blocks are harmful. Jump over them.
4. A descending landing on a walker removes that walker and bounces the player upward. Side or underside contact loses the run.
5. Reaching the end of the approximately 30-second course wins. One harmful collision loses. Restart restores the identical initial course; distance and stomp count are local run results.

Exclude coins, power-ups, ducking, health bars, multiple levels, checkpoints, enemy AI, combo systems, imported branded assets, and additional gameplay inputs from this first slice. Distinguish blocks and walkers by shape as well as color. The example needs one encounter that demonstrates a stomp followed by a useful bounce, not simply two unrelated obstacles.

## Smallest code pattern

Use **initial state → fixed-step update → draw**. Prefer ordinary functions and one small recipe over an ECS, plugin system, generic rule language, or another engine dependency. Minimize independently maintained behavior, not characters or line count.

| Piece | Minimal responsibility |
| --- | --- |
| State | Tick, feet height, vertical velocity, previous Jump state, remaining entities, stomp count and ready/playing/won/lost status. Derive distance and remaining time from tick. |
| Course data | A fixed list of block/walker positions, immutable dimensions and physics constants, finish tick and version. No random generator is necessary for the first example. |
| `step(state, jumpDown)` | Detect a fresh press; advance gravity/scrolling; resolve the earliest contact; update terminal state. No DOM, React, storage or network. |
| Contact response | Blocks and non-top enemy collisions lose. A descending top collision with a walker removes it and applies upward bounce velocity. |
| View/controller | Draw the current state, collect input, start/pause/restart and clear input on blur. Opening the introduction pauses an active demo without replacing its state. |

The semantic delta from a simple runner is one collision response:

```text
contact = first swept contact during this fixed step
if contact is a walker top AND player is descending:
    remove walker once
    apply upward bounce
else if contact exists:
    lose
```

This pseudocode describes the contact rule in `lib/party-forge/demos/dino-mario.ts`; see fresh validation results below. A top contact requires the previous feet to be above the enemy top and to cross it while descending, with horizontal overlap at the crossing time. Use interpolated relative positions or bounded substeps; checking only “airborne and overlapping” incorrectly rewards side hits. Resolve collision before finish when both occur on the last tick. A bounce must not generate another user input.

Retain the executable version, recipe and original assets in the repository/build. Restart means replaying those retained rules; it does not promise playback of a historical input recording or a durable saved game. Any future export should bundle this same source, not introduce a second HTML implementation.

## Onboarding behavior

On the first visit to the homepage in a browser session, show one modal introduction with no automatic gameplay:

> **Simulated demo · fixed authored example**
> **Dino × Mario**
> One jump. Two uses. Clear obstacles, then land on enemies to bounce ahead.
> This prepared example runs locally. Playing it does not generate a game or call AI.

Actions: **Try simulated demo**, **Skip introduction**, and a visible close button. Try opens `/play/dino-mario`; the game waits for **Start**. A persistent **How this remix works** action reopens the introduction. Show Source / Forge interpretation / User decision in accessible details before play and on the demo page.

Use native dialog behavior with an accessible name, keyboard containment, Escape, initial focus on a deliberate action and focus restoration to the opener. Store only a versioned session dismissal preference, with an in-memory fallback when storage is unavailable. Dismissal, navigation and reopening do not mutate party or creator state. Reopening during the demo pauses it and requires explicit Resume after closing; it does not restart it.

The popup must scroll within narrow viewports, leave close/skip reachable and avoid decorative motion under reduced motion. Touch support is bounded to the same visible Jump button. No game loop runs on the homepage or behind a closed demo. Keep local scores labeled; do not show simulated participants or canned successful outcomes as observed evidence.
