# PC-11 — Explore visible adaptive difficulty without changing creative rights

**Status:** Idea retained for later evaluation; local draft only. No GitHub issue/PR created, verified, or assigned. This is not approved core-demo implementation.
**Proposed accountable owner / implementer:** Lance. **Reviewer and player-experience partner:** Kahhow, with an independent final reviewer if both coauthor changes.

## Outcome

Determine whether bounded, visible difficulty adjustment helps a group with different skill levels keep enjoying the evolving game. A strong player's challenge may increase, but the system must not secretly rewrite scores, creative eligibility, or the group's agreed rules.

Read [PRD](../../PRD.md), [PLAN](../../PLAN.md), [QUALITY](../../QUALITY.md), [AGENTS](../../AGENTS.md), and the accepted room/scoring/runtime contracts. The user's idea is intentionally preserved here; the trigger, policy, and fairness benefit remain hypotheses to test.

## Scope and file ownership

First deliver a policy/evaluation proposal in `docs/party-adaptive-difficulty.md` and fixtures in `tests/fixtures/party-difficulty/**`. If the group explicitly accepts that policy for implementation, proposed allowed files are `lib/party-forge/difficulty.ts`, `tests/party-difficulty.test.mjs`, and `tests/integration/party-difficulty.*`. Lance owns the algorithm. Any runtime/score/room/schema or manifest change requires an explicit shared-file handoff; Kahhow owns separately scoped settings/explanation UI. Do not use this backlog packet as permission to modify the current matched-trial contract.

Compare a small set of transparent policies using actual observed play: for example, opt-in between-round challenge adjustments derived from several completed rounds. Define the observation window, eligible metrics, confidence/minimum data, cap, reversal rule, and reset behavior before testing. A single successful trial or genre-specific skill is not a stable ability estimate. DNF, disconnects, automation, and incomplete runs must not create an apparent weak/strong-player signal.

Keep adaptation outside an active frozen trial. Explain any per-player differences before play. Preserve winner/loser edit rights as the accepted rule; adaptive difficulty cannot grant extra cards or quietly change who is eligible. Assess score comparability before ranking differently configured trials. If scores cannot be compared defensibly, keep the mode separate from ranked rounds rather than inventing normalization.

Test deliberate sandbagging, repeated wins/losses, sudden improvement, oscillation, new players, changed game versions, and a player who wants a consistent challenge. The existing reward for losing already creates incentives; avoid claiming adaptation removes them. Group consent and an off switch are required for any trial of the policy.

## Acceptance and planned validation

Agree success measures before the study: perceived fairness, understanding of adjustments, willingness to continue, runaway advantage, and score/eligibility integrity. Report participant counts, observations, exclusions, and uncertainty. Do not promise equal winning probability or universal fairness.

For any implementation run `npm run lint`, `npm run build`, `npm test`, independent complete-diff review, then another lint/build/focused-test run after fixes; also run relevant Worker/room and real browser checks. Planning-only work checks consistency and preserves the backlog; no runtime results are claimed.

**Timebox:** 6–10 hours policy/data review, then re-estimate. **Cut/rollback:** keep adjustments disabled if evidence or comparability is insufficient. Preserve raw results, disable the policy for future rounds, and never rewrite historic scores or saved recipes retroactively.
